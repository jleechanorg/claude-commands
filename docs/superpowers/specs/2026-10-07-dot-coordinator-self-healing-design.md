# Dot Coordinator Self-Healing Design

## Goal, modification, necessity, and integration proof

**GOAL:** Keep authorized portfolio work moving when a persistent Dot browser profile is busy, routed to the wrong account, or temporarily unable to prove a session, while preserving exact authorization and preventing duplicate sends.

**MODIFICATION:** Extend the new portfolio coordinator’s existing finite observation loop, receipt-safe sender, and Dot transport integration with typed session evidence, exclusive profile ownership, bounded recovery, and privacy-safe metrics. Do not add a daemon, generic orchestration framework, new credential store, or automated login bypass.

**NECESSITY:** An operator-reported run had three direct sends return `DOT_SENT_VERIFIED` with full-message readback on Linux. Two Mac-side reads later reported “not signed in,” while a read of the same Dot through Linux worked. The raw session-endpoint/status evidence is absent. This is an instrumentation gap; it does not establish that a valid session expired, that cookies are defective, or that copying cookies would fix anything.

**INTEGRATION PROOF:** Fault-injection tests must establish typed auth states, profile and lease ownership, complete model input, stable scheduling, grant integrity, bounded process cleanup, and send/readback deduplication. After those checks and independent review, the authorized pilot has 36 fixed schedule slots over `[T0, T0 + 43,200)` on one designated Linux owner. A schedule slot is a time opportunity; an account slot is one of three configured identities. Every schedule slot receives exactly one durable terminal accounting state, including non-send outcomes. A reserved pilot slot allows at most one actual transport submission, with no automatic retry; an uncertain result is terminal `send_uncertain_hold`. The sender ledger enforces at most 36 sanctioned real submissions total across the pilot, with no pilot retries; no slot promises a send. Before T0, confirm per-account grant headroom for the planned sender submissions in the private pilot ledger. Do not depend on the generic remote spend reserve/settle path, which is capability-blocked; this pilot does not provision or authorize monetary spend. Any paid external spend requires its own existing authority. Model-driver CLI use is already authorized. The pilot reports every outcome without requiring a made-up availability target.

## Coordinator driver and blocker contract

The coordinator must have an explicit model-driver adapter. AGY is the default driver; a caller may explicitly select Claude or Codex. All task-selection and message-drafting model decisions use this same explicit driver adapter (AGY default; Claude/Codex only by explicit choice); `model_admission` remains deterministic input completeness/admission only, never a second reasoning route. The adapter invokes the selected canonical CLI using its required full-permission transport, passes a secret-minimized task packet, captures the actual process result, and validates a `schema_version: 1` structured decision before acting; missing or unsupported versions yield `driver_error` and no effect. Because that driver can read host credentials and invoke the Dot transport directly, packet minimization is not a credential or OS boundary. Launch each call in a run-owned process group/session through the existing `modules/process_utils.py::run_bounded_command` helper using the durable CLOSED startup-gate protocol in §2. Extend that helper to perform bounded process-group shutdown and descendant verification after normal completion as well as timeout/error, and surface cleanup failures instead of swallowing them. Wait and verify that no owned descendants remain before the post-call audit or any sender action. A surviving process or unresolved ownership makes cleanup unverified, fails the audit gate and blocks sender dispatch. This is process cleanup, not containment: a full-permission CLI may deliberately detach, change groups or otherwise escape detection, so never claim that process-group cleanup prevents escape or provides a host-security boundary. Its prompt is decision-only: it emits proposed messages and judgments, while all Dot effects are performed by `sender.py`. Run each canonical CLI with its unchanged canonical full-permission transport and a dedicated per-call private working directory under `/tmp`, separate from the source worktree and pilot state directory. Put coordinator-directed inputs and outputs and any project/session files the canonical CLI writes within that workspace; do not alter source or pilot state or change canonical CLI/provider storage defaults. Canonical CLI-owned transcript storage outside the run directory remains a documented exception. The untrusted correlated Dot reply reaches a full-permission CLI and may contain prompt-injection text; packet minimization and the decision-only instruction do not create an OS or credential boundary. Canonical CLIs may retain their own session transcripts outside the run directory; delete only transient input/output files this coordinator owns, and make no claim that provider-owned transcripts are deleted. Public receipts and evidence never contain raw reply text, credentials or cookies.

At every schedule slot, after a typed probe and before phase/hold dispatch, audit the active account’s anchored configured conversation within the same cumulative +180-second probe/read/reply budget, regardless of phase (including delivery, lease, challenge and auth holds). The probe, audit and any due correlated-reply read share this single ceiling. A probe that cannot establish a usable account-correct local profile or open the configured conversation records its exact typed probe state plus `audit_status=deferred`; that failed probe does not also emit a conflicting `message_audit_unknown` slot outcome or set an audit hold by itself, and it permits no model/sender work. Map the typed probe state to its ordinary closed outcome in §5. Maintain a per-account `last_complete_cursor` initialized to the preflight anchor. Each audit reads only the incremental range from that durable cursor to a complete end cursor, records the segment boundaries and digest, and advances the cursor atomically only after the segment is fully verified. Link each segment to the preceding segment digest so the final chain proves cumulative coverage from the anchor without rereading the growing full history. Use transport-proven half-open boundaries `(start_cursor, end_cursor]`: the next segment starts at the preceding complete end, never recounting its boundary message. Bind each chained digest to run/account/conversation, preflight anchor, ordered message IDs/actor-binding receipts/content digests and completeness evidence, both cursors and the preceding digest. Each segment independently requires feasibility-proven complete boundary/order evidence; digest continuity alone never establishes completeness. Commit the segment, chain head and `last_complete_cursor` in one atomic run-state replacement; incomplete reads commit no progress. Post-driver and final audits use this same chain and read only its unaudited tail plus feasibility-proven revision observations for prior IDs, then verify cumulative coverage from the preflight anchor. Append observed revisions with previous digest linkage; a same-ID content change is not a duplicate submission or completed turn, and unproven revision coverage remains unknown. A deferred interval is covered by the next complete segment beginning at the last durable cursor; gaps, overlaps, cursor regression or a broken chain remain unknown and block pass. The feasibility spike must measure requested/returned message counts, bytes, pages and read duration across increasing ranges, including deferred backlogs, against the shared +180-second probe/read/reply bound; record probe overhead and remaining read time, maximum demonstrated range and explicit GO/NO_GO threshold. Ranges beyond measured capability remain unproven; do not infer bounded latency from one small range. Only a usable account-correct probe followed by an incomplete/late +180-second conversation audit produces `message_audit_unknown` and an account audit hold. This per-slot audit is the cross-account detection point: each account is checked on its next slot before driver work, including slots that otherwise would not invoke a driver; detection may be delayed until that slot and cannot prevent a bypass. Separately, before each driver call, durably mark a per-account `pending_audit` in private `run_state.json` together with the exact source snapshot and private-state audit baseline. After the call, audit the protected source-worktree snapshot, coordinator-owned private run state (including the process submanifest and frozen `wrapper_state.json` identity/bytes/digest), submission-count ledger, outbound spool, grants/leases, process cleanup, and the active account’s configured Dot conversation for driver-caused effects within the existing post-driver +540-second cumulative budget. If the audit fails, stop dispatch. Do not digest the shared Beads database as coordinator-private state; preserve its existing CAS contracts, but unrelated legitimate Beads writers must not trigger the pilot audit. The observer retains the existing process-level `coordinator.lock` ownership for its lifetime. Within that owner, a single in-process standard-library `RLock` synchronizes the in-memory expected-write ledger with brief heartbeat/state writes and audit snapshots/checks. Do not reacquire the process lock through another file descriptor, which can self-deadlock, and do not hold the in-process lock across driver/model or network calls. For the source-worktree audit set, require the dedicated frozen implementation worktree to have `HEAD` equal to the pilot code SHA and a clean `git status --porcelain --untracked-files=all` before T0. The exact tracked-path set comes from `git ls-files --stage -z`; do not read `.env` or credential contents—exclude those pathnames from byte hashing, record the exact excluded path list by name only, and make no claim about them. Snapshot every other tracked path, recording path bytes, file type, mode, symlink target or regular-file SHA-256; this is the immutable source baseline. Ignored files and `.git` internals are excluded and are not inspected; make no coverage claim about them. No concurrent writer may touch the implementation worktree during a driver call or pilot; any tracked-file difference, staged change, non-ignored untracked path, rename, deletion, mode/type change, or HEAD movement fails the audit and durably stops dispatch, regardless of originating client. Recheck HEAD, complete non-ignored status, and each baseline path/hash after the driver call. Add a fixture that changes a tracked in-scope source file during a driver call and proves stop-before-sender behavior. For coordinator-owned `run_state.json` and `heartbeat.jsonl`, record exact replacement/append bytes and resulting file identity in the same brief critical section as each parent-owned write; snapshot identities/contents before the driver call and verify only those exact write records after stopping owned descendants. Unrecognized private-state writes, rewrites, truncations or inode changes also fail the audit and stop dispatch. Test a heartbeat and lease renewal during a long driver call, plus an unrecognized concurrent mutation. Only after the post-driver audit completes and its result is durably recorded may `pending_audit` clear. On every startup or restart, verify and reap exact recorded owned browser/Node/driver orphans under §2, then inspect `pending_audit` before any new driver, sender or profile reuse; cleanup never clears that marker or recovers lost audit provenance. If the coordinator crashes while this marker is set, the in-memory expected-write ledger is lost: fail closed by durably setting run-stop and account audit-hold, account the remaining slots as `pilot_stopped`, and do not invent a recovered audit or invoke another driver/sender. This is an explicit self-healing safety limit. The active-account audit detects cross-account messages only when that account’s next slot reaches its pre-driver audit or at final audit; detection is delayed and cannot prevent the bypass. A detected violation stops dispatch from that point. This does not assert actor attribution from file shape alone or broaden the protected-state scope. Establish a per-account preflight history anchor; compare all newly observable authenticated-session-actor submissions through a complete end cursor with sender receipts. Any complete authenticated-session-actor submission in the audited range lacking an exact sender receipt fails the pilot regardless of originating client, including a bypass submitted as the same logged-in session actor. Every complete non-session-actor message remains in the digest chain as a non-submission, regardless of reply anchors. Missing/ambiguous actor evidence yields `message_audit_unknown`, never a pass or role-based violation. Reconcile pending `submitting`/`send_uncertain_hold` entries first under §1 before classifying a landed session-actor message as unreceipted. Before T0, verify known automated writers are paused or covered by the pilot-owned lease. The lease cannot prevent external human activity; report this as an assumption, and fail on any complete unexpected authenticated-session-actor submission without inferring the initiating client or requiring a new exclusivity promise. The CAS-protected 36-total/12-per-account cap is preventive only for sanctioned sender submissions; the full-permission driver can bypass it. Audit is detection-only within the configured complete ranges, and cannot make a host-security or universal cap claim. If readback completeness cannot be proved, emit `message_audit_unknown`, fail the audit gate and make no claim about messages outside the observable range. Preserve the required full-permission invocation. A worktree isolates files and branch state, not host access.

The packet contains the authorized task context, current authority gates, complete blocker evidence and source receipts, attempts/outcomes, remaining authorization, safe independent work, and the complete set of mechanically authorized task candidates with each candidate's exact source-record binding. It excludes credentials, cookies and unrelated private content. The one correlated Dot reply is permitted private decision input under the channel below. The selected driver model owns task selection from those mechanically authorized candidates and owns blocker judgment and message drafting; deterministic filtering enforces grant, scope, source-authority and record-integrity constraints only. It does not decide semantic eligibility, priority or current viability. The driver returns a structured decision only; it never invokes Dot transport. `sender.py` is the only dispatch path for inventory and challenge messages. For a selected candidate, before browser/composer setup the sender re-reads that task's authoritative source receipt, version and digest as well as reservation, grant/scope/version/digest, identity, deadline and fencing. Immediately after warm-up and eligibility waiting, obtain a fresh sender authorization for the irreversible action by rechecking those same values plus spacing; this handshake makes no model call. The transport must not execute the irreversible action unless this authorization is current. At stage entry, re-read the active task's fresh source record and verify that it remains present and authorized; pass the fresh receipt together with the prior reply and prior source provenance to the model so it can judge the change. A source-record update alone does not invalidate the cycle. If the task is missing or no longer authorized, invalidate the cycle and set `inventory_due`; grant invalidity retains its higher-priority outcome. If the source changes after drafting but before sender commit, abort the irreversible action and record `no_action`, retaining the safe current phase for model re-judgment next slot; never send a stale proposal. Preserve grant-invalid and unresolved delivery-hold precedence. Measure `last_actual_submission` after the final checks and immediately before the irreversible transport action. In `inventory_due` or `cycle_complete`, the driver decides whether any supplied authorized candidate is eligible and currently viable; if so, it selects exactly one and proposes an evidence-backed inventory request tied to that task's exact source-record binding and reserved event ID. The model may return typed `no_eligible_task` with `action=no_action`, null task/source bindings and its judgment whether the candidate set is empty or nonempty; backend code does not make that semantic decision. After an authenticated anchored reply observation, the driver asks which blockers prevent progress and what safe action can unblock them, then reads Dot's reply. While blockers remain, continue the existing challenge/read loop within authority and budgets. Once the observed reply supports that blockers are resolved, ask Dot its priority and which single action it will do now, then read that reply. Record whether the last receipted challenge asked about blockers or priority in the existing account phase state; this is question bookkeeping, not a new transport protocol. After observing the priority/action reply, any requested "continue" instruction is a separate `stage=challenge`, `outcome=send_proposal`, `action=send` proposal dispatched only by sender under current grant/source/scope, owner, budget and physical-deadline checks. Dot's stated priority is not authority for an instruction. Count that outbound instruction as its own one attempt in the current slot and against the same per-account/total caps, with normal uncertainty/no-retry handling. Persist its ordinary sender receipt before a later-slot non-sending `final_judgment`; never send through final judgment or combine two driver calls/sends in a slot. When no continue instruction is authorized/requested, final judgment may follow the priority/action observation without sending. `no_action`/`cycle_complete` means the coordination exchange ended, not that Dot's turn or task completed. Another inventory waits for the next account slot. Persist each phase and receipt by account; the authoritative phase and reply schedule is in §5.

### Versioned driver decision schema

Version 1 preserves the existing top-level `event_id`, `task_id`, `stage`, `blockers`, and `message` fields and adds a closed typed `outcome`. For `inventory`, the input contains the complete mechanically authorized candidate set with each candidate's `task_id` and `source_binding`; grant, scope, source authority and record integrity are mechanical filters, while the model owns candidate eligibility, priority and current viability. The model selects exactly one candidate for a `send_proposal`, or may return `outcome=no_eligible_task`, `action=no_action`, `task_id=null` and `source_binding=null` for either an empty or nonempty candidate set, accompanied by its structured judgment. Backend code must not infer this outcome from candidate count or classify candidate semantics. For `challenge` and `final_judgment`, the input is already bound to one task and its source receipt, which the response must match exactly. Every response has these fields and types:

| Field | Required form |
|---|---|
| `schema_version` | Integer `1`; absent/unsupported versions are `driver_error` with no dispatch. |
| `event_id` | Non-empty string exactly matching this reserved schedule-slot event. |
| `task_id` | Exact selected candidate task for an inventory `send_proposal`, or exact pre-bound task for `challenge`/`final_judgment`; null only for typed `no_eligible_task` during inventory selection (in phase `inventory_due` or `cycle_complete`). |
| `outcome` | Closed enum `send_proposal`, `no_eligible_task`, or `cycle_complete`; `send_proposal` requires `stage=inventory` or `challenge` and `action=send`; `no_eligible_task` requires `stage=inventory` and `action=no_action` with null task/source bindings, regardless of candidate count; `cycle_complete` requires `stage=final_judgment`, exact task/source binding and `action=no_action`. |
| `stage` | `inventory`, `challenge`, or `final_judgment`, exactly matching the input phase. Inventory selection is called for `inventory_due` or `cycle_complete`; final judgment is called for `challenge_reply_due` after the observed priority/single-action reply when no continuation send remains, or at the next slot after a receipted continue instruction. Follow-up questions and any authorized continue instruction use `stage=challenge`; `final_judgment` cannot send. |
| `source_binding` | `{source_id: string, task_composite_key: [string,string,string,string], record_version: string, record_digest: 64-char lowercase hex}` matching the selected candidate receipt for an inventory `send_proposal`, or the exact input-bound task receipt for `challenge`/`final_judgment`; null only with typed `no_eligible_task`. |
| `grant_binding` | `{grant_version: positive integer, grant_sha256: 64-char lowercase hex}` matching the current pinned grant. |
| `correlation` | `null` only for inventory selection; otherwise `{parent_event_id: non-empty string, user_message_id: non-empty string, assistant_message_id: non-empty string, start_cursor: non-empty opaque string, end_cursor: non-empty opaque string, complete: true}` exactly matching the observed actor/room/anchor-bound reply receipt below. These legacy field names denote the receipted session submission and target-Dot reply IDs, not raw transport roles; `complete: true` denotes verified coverage of the observed range only, never final reply text, Dot-turn or task completion. The private receipt also binds the exact observed revision digest; no completion signal is inferred. |
| `judgment` | `{assessment: "blocked"|"not_blocked"|"unknown", safe_next_action: string}`; these are model-owned semantics, never recomputed from prose or keywords. |
| `blockers` | Existing bounded list of objects with exactly `description`, `evidence`, `attempts`, `missing_capability_or_approval`, and `independent_work`, each a string. |
| `action`, `message` | `action` is `send` or `no_action`; `send` requires a non-empty `message` string; `no_action` requires `message: null`. `challenge` after an authenticated anchored reply observation uses `send_proposal` for the next blocker/safe-unblocking-action question, or the priority/single-action question once blockers are resolved, or an explicitly authorized/requested continue instruction after its reply, subject to busy-generation and other safety holds. `final_judgment` must be `cycle_complete`/`no_action` and cannot include a new inventory proposal. |

The coordinator builds candidate bindings from a fresh complete `PortfolioCollector.collect_source_snapshot` for the selected source(s), matching each exact `task_composite_key`. Mechanical filtering applies current grant/scope, source authority and record-integrity constraints, but does not infer semantic task eligibility or viability; the complete authorized candidate set is sent to the model. The model selects one candidate or returns its typed `no_eligible_task` decision, and the selected source record is re-read before dispatch. For already-bound `challenge` and `final_judgment` stages, the binding is inherited from the active cycle. For `no_eligible_task`, no task binding is returned whether the candidate set is empty or nonempty. The record version is the task's own source version (for example its `updated_at`), and `record_digest` is SHA-256 of the canonical sanitized item. The whole-source snapshot version is retained as freshness provenance only and does not invalidate a cycle when an unrelated item changes. At each challenge/final-judgment stage entry, re-read the selected task by exact composite key, confirm it is still present and authorized, then give the model the fresh record receipt plus the older source provenance and correlated reply. The model judges whether ordinary task updates matter; code does not restart the cycle merely because `updated_at` or another non-authority field changed. Task disappearance or loss of source/grant/scope authority invalidates the active task; ordinary source updates do not. At pre-setup and irreversible-send checks, refresh the source and require `status=fresh`, `cursor.completed=true`, `checkpoint_committed=true`, and the same composite key. If the record version/digest changes after drafting while the task remains present and authorized, block the stale send, retain the safe phase and re-judge on the next slot; if the task is absent or loses authority, invalidate it. Missing or partial source evidence blocks the irreversible action.

The adapter validates this exact schema and shape, then the sender independently rechecks every binding against the current reservation, task receipt and grant before dispatch; any absent/mismatched field rejects before irreversible action. It does not infer blocker meaning from `judgment`, `blockers`, `message`, or any other narrative.

Every blocked report must state the observed blocker, evidence and provenance, attempts and outcomes, exact missing authorization or capability, and what can still proceed. Dot reports its blocker inventory and own work state in response to sender-dispatched prompts; the selected driver model judges whether work is blocked and what coordination action remains safely possible. A missing permission or failed tool alone must not erase independent authorized work. If the model call fails, times out, returns malformed output, or chooses an unavailable driver, report that driver failure truthfully and preserve the task for retry; do not convert it into a semantic `capability_blocked` decision or claim the task itself is blocked. Extend the existing selected `DriverAdapter` for this contract. `admit_model_transport` is a separate capability-blocked generic model-isolation path, not the selected driver route; do not wire model reasoning through it or claim it implements this behavior.

## Observed behavior and uncertainty

The supplied event report is evidence about transport outcomes, not a diagnosis. The observed Linux sends were verified by the transport marker and complete submitted-message readback. The Mac path’s two “not signed in” reports lack the raw `/api/auth/session` status and profile identity needed to distinguish genuine logout from a host/profile mismatch, cross-host route issue, concurrent profile use, or incomplete probe. Linux subsequently read the same Dot successfully. The design therefore treats any status lacking the required endpoint and identity evidence as `unknown`, not as logout.

Before T0, parent resolves each existing operator-owned selector to exactly one existing Chrome Local State profile identity, confirms distinct records, and records selector-match strength. A selector may match by name or domain; the uniquely resolved stored profile record itself must contain a usable account email. Freeze the digest of that stored email plus source-record references/digests in protected machine-local pilot configuration before any live session-endpoint comparison; do not expose the raw email. At runtime require an exact digest match between the session endpoint's account email and this frozen stored-record email. If the stored record has no usable email, report `identity_attestation_unavailable`; if the Dot session email differs from the selected Chrome profile record, report `identity_mismatch` and do not fall back to another profile or route. This does not require the selector itself to contain an email and creates no new human-approval gate. This reuses existing configured identities and requires no new human approval. Do not invent or auto-attest an identity: if existing records are missing, ambiguous or inconsistent, record `identity_attestation_unavailable` and do not start T0. Never learn or revise the expected digest from the live endpoint (no trust-on-first-use). After freezing each expected digest, run a read-only local `/api/auth/session` identity probe for every account before T0; all three must exactly match or T0 is blocked. The newest verified canonical reads/deliveries are healthy for all three configured accounts (nine verified deliveries). This supersedes the two-account-unavailable claim but does not establish typed exact-identity attestation or anchored complete-history feasibility; both remain unproven. Historical exploratory identity observations do not establish the current typed all-account preflight or safe launch ownership proof. The normal Linux launch path calls `ensurePersistentProfile`, which refreshes the existing cookie database from its configured source when its mtime is older than ten seconds (`fs.copyFileSync`), despite a nearby “never overwrite” comment. The pilot’s existing-profile-only probe deliberately skips that copy/refresh; this preserves the no-cookie-copy constraint but may omit normal maintenance relied on by some profiles. Do not claim this probe repairs login or preserves every normal-path session. The planned typed probe must distinguish Cloudflare challenges and 403 responses from a genuine logout, and call genuine logout only for a successful empty-user session response or an explicit login action. Its `DOT_SENT_VERIFIED` result includes exact composer matching, composer clearing after the send, and the submitted authenticated-session-actor submission appearing in the conversation. The login command opens the resolved profile for ordinary manual sign-in. Existing local profile selection is the only pilot route; configured cross-host forwarding is future conditional mode only; they do not authorize copying cookies or bypassing security challenges.

## Alternatives and recommendation

| Approach | Benefit | Cost or failure mode |
|---|---|---|
| Ask for manual sign-in whenever one host reports “not signed in” | Simple and conservative | Blocks authorized work while a correct local or configured remote profile may still be healthy; repeats the observed false stop. |
| Add monitoring only and keep current sender decisions | Smallest code change | Makes the failure visible but does not serialize profile access, recover stale owned processes, or protect retries after an uncertain delivery. |
| **Recommended: typed probe and bounded recovery inside the existing coordinator and Dot transport** | Reuses current profile resolution, transport, control journal, sender, and finite observe loop; can distinguish recoverable local conditions from a genuine security boundary | Requires explicit structured probe results and focused fault-injection tests before the live pilot. |

Do not reset/recreate browser profiles or copy cookies. Those choices invalidate a healthy session, weaken profile ownership, and still do not prove the target identity.

## Recommended architecture

### 1. Typed, privacy-safe session evidence

Add read-only status/probe and bounded message-read operations to the existing Dot transport. During the pilot, use local route only; `DOT_NO_REMOTE=1` forbids all remote probes, commands, and forwarding, including on `human_auth_required`. Future cross-host use is a separate conditional mode. The transport returns a machine-readable result with required integer `schema_version: 1`; missing or unsupported versions map to typed `unknown` and a no-send hold, never to inferred status. Use distinct closed types: `AuthState` is the seven-value `auth_state` enum below; `SlotOutcome` is the terminal enum in §5. Recovery retains the typed probe evidence until the single phase-aware mapping in §5 determines an outcome. Do not conflate probe states, dialogue phases and terminal outcomes. Fields:

- `schema_version`: exactly `1`; reject absent or unsupported versions as `unknown`/no-send;
- `auth_state`: `authenticated`, `genuine_logout`, `challenge`, `lease_busy`, `profile_mismatch`, `transport_error`, or `unknown`;
- `identity_match`: `true`, `false`, or `unknown`, true only when the session endpoint email exactly matches the frozen digest of the usable email in the uniquely resolved stored Chrome Local State identity record; the selector itself may be name/domain based, but cannot supply the email. A missing or ambiguous stored identity record is the pre-T0 blocker `identity_attestation_unavailable`, not an `AuthState` or `SlotOutcome`; at runtime it maps to `identity_match=unknown` and `probe_unknown`. A different Chrome-record and Dot-session email is `profile_mismatch` with no profile/route fallback. Never expose either identity or digest;
- `composer_state`: `ready`, `busy`, `unavailable`, or `unknown`, observed without editing or clearing the composer; active generation maps to busy and unverifiable send readiness to unknown, blocking a new submission without turning an idle composer into proof of Dot-turn/task completion;
- `route`: `local` or `configured_remote`, plus a non-identifying host role;
- `profile_slot`: public opaque account-slot label, distinct from the private canonical account/profile identity; expected identity digest is pinned in protected local pilot configuration only after resolving the existing account selector to one stored Chrome Local State identity record with a usable email; the selector may be name/domain based. Freeze that stored-record email digest before any live endpoint comparison and require exact session-email match; never use the live endpoint for trust-on-first-use or fall back on mismatch;
- `probe_id`, UTC timestamp, endpoint status class, and bounded diagnostic code. The message-read operation accepts only configured conversation(s) and an anchor; it returns message IDs, complete start/end cursors and an internal exact-text comparison result plus digest only for caller-supplied expected payload. The public/status result never returns or logs message text. A separate lease-bound private reply channel supplies the single correlated reply to the selected driver as specified below. Track each observed revision by message ID, observation cursor/time, content digest and prior revision digest. Changed text at the same ID is not by itself a violation or completion signal; preserve prior revisions and require complete revision coverage as specified below. Audit is scoped only to configured conversations and cursor-complete ranges. Any complete readable authenticated-session-actor submission in the audited range that lacks an exact sender receipt is an audit violation and stops dispatch, regardless of whether it came from a model bypass, operator, or another client. Incomplete/uncertain ranges or actor bindings yield `message_audit_unknown`; never infer actor identity from CSS, display name, message text or raw role. Before T0, verify known automated writers are paused or covered by the pilot-owned lease. The lease cannot prevent external human activity, so state this as an assumption rather than a guarantee or new approval gate. This does not prove absence outside that range or in other conversations.

Read the auth response body only in memory as needed to parse the account identity and compare it with the frozen digest sourced from the stored profile record; immediately reduce it to status and `identity_match`, then discard it. Never persist or log the raw auth body, tokens, cookies or email; the explicitly required private session/actor binding below is retained only as minimized receipt provenance, never public identity output. Public artifacts and public receipts exclude private identity and conversation text; only the private actor/room/anchor receipt provenance below is retained. The correlated target-Dot reply is untrusted input and may contain prompt-injection text. The trusted read operation may deliver it to the coordinator in memory, and the coordinator may pass it through private stdin to the selected full-permission driver; this is an accepted exposure, not a security boundary or authority grant. When a canonical CLI needs a prompt file, permit one owned mode-0600 input file inside the per-call private mode-0700 `/tmp` driver workspace, delete that coordinator-owned file after the call, and delete owned leftovers on restart. A canonical CLI may persist its own session transcript outside this directory; do not claim to delete or control provider-owned files. Never place raw reply text in coordinator receipts, captures, public logs or evidence. Receipts never contain raw reply text; retain its digest/message ID plus the explicitly required private actor/room/anchor evidence below. This is a sanctioned lease-bound channel, so the driver never needs to read Dot itself. Canonical CLI session transcripts may retain this untrusted reply and task context outside the run directory; only coordinator-owned transient files are deleted, and published evidence never contains the raw reply.

For crash-safe exact outbound readback, preserve the submitted outbound payload in an owned mode-0400 private spool keyed by event ID and digest, under the same private run directory and exact-file manifest. It is unavailable to public/status output.
