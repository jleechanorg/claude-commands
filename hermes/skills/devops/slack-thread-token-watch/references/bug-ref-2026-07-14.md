## Why it failed

`babysit-ao-pr-loop` Phase 0 is structured around:

1. `gh pr view <PR>` for terminal-state probe.
2. `ao session ls | grep <worker>` for worker-state probe.
3. `git log origin/<base>..HEAD --oneline` for change detection.

None of these have a meaningful answer for a literal-token watch loop:

- No PR → gh pr view returns empty / undefined.
- No worker → ao session ls returns empty.
- No branch → git log returns empty.

The babysit's "did anything change" gate trips immediately, the cron emits a
single heartbeat, and Phase 0.5 self-cancels the cron. **Clean failure mode —
but the operator never finds out the watch loop died.** The "babysit armed"
claim was a lie, and the gate stayed silent until the next disk-alert firing
in another alert cycle.

## What should have happened

The cron prompt should NOT have passed `--skill babysit-ao-pr-loop`. The
right pattern is a tiny custom prompt with:

1. `conversations.replies` substring scan (no PR + AO worker involvement).
2. Optional destructive callback (with path whitelist + age + locked filters).
3. `hermes cron remove $CRON_JOB_ID` on first match or age-out.
4. One heartbeat per cadence if nothing changed and no match.

That is exactly the `slack-thread-token-watch` skill this file belongs to.

## Diagnostic recipe

When a "watch loop" is supposedly running, verify it is actually running:

```bash
# 1. Confirm the cron is still in the registry
hermes cron list | grep -i "<job-name>"

# 2. Confirm the cron-output dir has fresh entries
ls -lt ~/.hermes/cron/output/<job_id>/

# 3. Confirm the parent thread has a recent heartbeat (if cadence > 30 min,
#    there might be no heartbeat posted yet — that is expected for the
#    SILENT contract; check the cron-output dir instead)

# 4. Confirm the executed-flag is set if the work already fired
ls -la /var/tmp/<job_id>_executed 2>/dev/null || echo "no executed flag"

# 5. Confirm the eligibility list is intact
ls -la /tmp/eligibility.json 2>/dev/null || echo "eligibility list missing"
```

If (1) is empty, the cron self-cancelled. The most likely cause is the
wrong skill auto-loading, as in this bug-ref. Re-author the cron WITHOUT
the wrong-skill flag and verify the next tick produces a heartbeat that
matches the expected cadence.
