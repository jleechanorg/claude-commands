# UPSTREAM-PROMPT.md format reference

Canonical structure of the instructions file that often accompanies a
supplied patch. Knowing what each section typically contains lets the
agent extract the right info without parsing-the-prompt improvisation.

## Filename conventions

| Filename pattern | What it usually is |
|---|---|
| `UPSTREAM-PROMPT.md` / `upstream-prompt.md` | Most common — instructions for upstream contribution |
| `RUNBOOK.md` / `runbook.md` | Operational/SRE instructions (similar shape) |
| `HANDOFF.md` / `handoff.md` | Cross-session handoff with reproducible commands |
| `<name>-PROMPT.md` | Project-specific prompt file naming |
| `INSTRUCTIONS.md` / `TASK.md` | Generic task instructions |
| Embedded in the patch trailer | Less common — `git format-patch` `--signoff` can include hints |

## Section-by-section expected content

```
# Prompt: <one-line summary>
Brief context: what this patch does, in 1-2 lines.

---

## What the feature is
Detailed description of the new behavior. Read this BEFORE touching code —
the bullet points often map 1:1 to the files the patch touches.

## Steps
1. clone
2. branch
3. git am (with --3way fallback if it fails — exact conflict points listed)
4. verify (test paths, lint commands, ALL listed)
5. push
6. open PR (title template + body template, often quoted verbatim)
7. do NOT merge — leave for repo owner

## Guardrails
- Files NOT to add (e.g. "no findings_wiki/* files except README+TEMPLATE")
- Paths NOT to leak (e.g. "no /Users/<name>/...")
- Purity invariants (e.g. lint commands that must return clean)
```

## Section extraction patterns

When the script `scripts/apply_patch_and_open_pr.sh` parses the instructions
file, here's what each grep target looks for:

```bash
# PR title — usually the first H1 heading
PR_TITLE=$(grep -E '^# ' "$INSTRUCTIONS" | head -1 | sed 's/^# //')

# Test suite paths — usually `bash tests/<name>.sh` lines
TESTS=$(grep -oE '(bash|sh) [^ ]*test[^ ]*\.sh' "$INSTRUCTIONS" | awk '{print $2}')

# Lint / purity check commands
LINT_CMDS=$(grep -oE '(bash|sh) [^ ]*(lint|purity)[^ ]*\.sh[^"]*' "$INSTRUCTIONS")

# Expected base SHA — usually in the first paragraph ("authored against
# origin/main at commit <sha>")
BASE_SHA=$(grep -oE 'commit `?([0-9a-f]{7,40})`?' "$INSTRUCTIONS" | head -1)
```

## What to do when a section is missing

| Missing section | Fallback |
|---|---|
| No "What the feature is" | Read the patch's commit message — usually summarizes it |
| No "Steps" but lists tests inline | Run the tests, then push + open PR with a body built from the patch's trailer |
| No PR title | Use the patch's commit subject (`Subject: [PATCH] <title>`) |
| No PR body template | Build one from the patch + the test results |
| No "Guardrails" section | Default to: no machine paths, no unrelated file additions. Run `git diff --stat origin/main..HEAD` and verify the file count matches the patch's intent. |

## Worked example

`UPSTREAM-PROMPT.md` for the jleechanorg/disk_magician PR #17 evidence run
(this skill's verified case):

- Title line: `# Prompt: apply the findings_wiki + safety.local.json contract to upstream disk_magician`
- "What the feature is" — 8 bullet points covering the two layers (enforcement + knowledge), the wired cleanup scripts, the test count
- "Steps" — exactly 7 numbered steps, ending with "Do NOT merge — leave the PR for the repo owner"
- "Guardrails" — 3 bullets covering file purity invariants, no machine paths, port-the-gate-pattern for unrelated cleanup-script refactors

The agent's job is to extract this structure, follow Steps 1-7 verbatim,
honor the Guardrails, and not improvise.

## Anti-patterns

1. **Don't reformat the user's PR body template.** If they wrote it
   indented for markdown, paste it indented. Their PR description is the
   deliverable; rewriting it loses the user's authorship voice.

2. **Don't add "Generated by [skill]" footers.** The user expects the PR
   description to come from the instructions file. Adding a footer
   changes the diff in a way that doesn't add value.

3. **Don't cite yourself in the PR body.** "I ran the tests with..." is
   a first-person narration that doesn't belong in an upstream PR. Save
   the first-person narration for the Slack reply, not the PR description.

4. **Don't merge the PR even if you could.** The instructions file
   almost always says "leave the PR for the repo owner." That maps to
   SOUL.md merge discipline: no merge without `MERGE APPROVED`.
